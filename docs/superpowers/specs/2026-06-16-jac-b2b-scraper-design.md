# JAC B2B (b2b-jac.com) — сбор остатков и цен

Дата: 2026-06-16
Статус: согласовано к реализации (пользователь предварительно авторизовал автономную разработку)

## 1. Задача

Поставщик JAC предоставляет B2B-портал (https://b2b-jac.com) на 1С-Битрикс.
API-ключа нет (в отличие от трёх других поставщиков). Нужно автоматически
собирать **остатки (наличие)** и **цены** по технике/номенклатуре, парся
портал, и складывать результат в формат, пригодный для объединения с данными
остальных поставщиков.

Главный источник данных — страница «бланк заказа»
(`/orders/blank_zakaza/000000002/`): на таких страницах Битрикс выводит весь
прайс-лист со складскими остатками и ценами. Это удобнее, чем обходить каталог
по категориям.

## 2. Что выяснено при разведке

- CMS: **1С-Битрикс** (`X-Powered-CMS: Bitrix Site Manager`).
- Форма авторизации: POST на `/?login=yes`, поля:
  `AUTH_FORM=Y`, `TYPE=AUTH`, `backurl=/`, `USER_LOGIN`, `USER_PASSWORD`,
  `USER_REMEMBER=Y`, `Login=Войти`.
- Сессия держится на cookie `PHPSESSID` (+ `BITRIX_SM_*`).
- Страницы рендерятся на сервере → достаточно HTTP-клиента (`requests`),
  headless-браузер не обязателен.
- **Блокер:** есть пароль (`выдан владельцем`), но **нет логина**. Комбинация
  логин=пароль даёт «Неверный логин или пароль». Подбор логина не делаем
  (Битрикс включает CAPTCHA/блокировку после серии неудач). Логин обязан
  предоставить пользователь — это единственный недостающий вход.
- Сетевое окружение песочницы навязывает Python-у SOCKS-прокси
  (`socks://127.0.0.1:10808`); прямой доступ работает. В коде используем
  `session.trust_env = False`, чтобы клиент ходил напрямую на любой машине.

## 3. Стратегия авторизации

Поддерживаем два способа (оба не требуют от меня хранить «угаданные» данные):

1. **Логин + пароль (основной).** Пользователь вписывает `JAC_LOGIN` в
   `config/.env` (пароль уже подставлен). Скрапер сам POST-ит форму Битрикса и
   держит сессию. Полностью автоматизируется (планировщик).
2. **Импорт cookie (резерв).** Если логин неизвестен/неудобен, пользователь
   копирует cookie своей уже залогиненной сессии (`PHPSESSID` и др.) из браузера
   и вставляет в `config/.env` (`JAC_COOKIE=`). Скрапер ходит с этой cookie.
   Чести «я уже залогинен» — этот путь использует существующую сессию без
   передачи пароля. Минус: cookie живёт ограниченно, для ежедневной
   автоматизации лучше способ 1.

Реальные cookie из браузера не вычитываем автоматически (песочница это
обоснованно блокирует как сбор учёток) — пользователь делает это сам, осознанно.

## 4. Архитектура

Python 3.13, чистый HTTP (`requests`) + `BeautifulSoup`/`lxml`. Модульно:

| Модуль | Назначение | Зависит от |
|---|---|---|
| `config.py` | читает `config/.env`, валидирует настройки | python-dotenv |
| `session.py` | строит `requests.Session` (`trust_env=False`), логинит по паролю или подставляет cookie, проверяет факт авторизации | config |
| `catalog.py` | тянет страницу(ы) бланка заказа и каталога, обрабатывает пагинацию/AJAX | session |
| `parse.py` | превращает HTML строки таблицы в нормализованные `Product` (артикул, наименование, бренд, остаток, цена, ед., валюта) — устойчивые эвристики | bs4 |
| `discover.py` | режим калибровки: сохраняет сырой HTML и авто-определяет таблицы/колонки/ссылки экспорта, чтобы донастроить селекторы под реальную верстку | bs4 |
| `export.py` | пишет нормализованный CSV / XLSX / JSON | openpyxl |
| `models.py` | dataclass `Product` + нормализация чисел («1 234,50» → 1234.5) | — |
| `cli.py` | команды: `check`, `discover`, `scrape` | все |

Поток: `cli.scrape` → `session.authenticate()` → `catalog.fetch_blank()` →
`parse.parse_products()` → `export.write()`.

### Почему discovery-first
Аутентифицированный HTML бланка заказа я сейчас не вижу (нет логина), поэтому
точные CSS-селекторы колонок неизвестны. Парсер написан на устойчивых
эвристиках (строка = товар, если содержит артикул + числовую цену + индикатор
наличия) и покрыт тестами на фикстуре типичной верстки Битрикса. Команда
`discover` на первом же реальном входе сохранит настоящий HTML и предложит
карту колонок — за 5 минут селекторы калибруются под факт. Так решение
максимально готово к моменту, когда появится логин.

## 5. Модель данных (нормализованная)

`Product`: `article` (артикул/код), `name`, `brand`, `stock_qty` (число или
текст наличия типа «много/под заказ»), `stock_raw`, `price`, `currency`
(по умолч. RUB), `unit`, `warehouse` (если есть), `source="jac_b2b"`,
`scraped_at` (ISO-время).

Экспорт-схемы:
- `stock_<дата>.csv` / `.xlsx` — человекочитаемо.
- `stock_<дата>.json` — для интеграции с агрегатором четырёх поставщиков
  (единый список объектов Product). Маппинг под точную схему остальных трёх
  поставщиков — отдельный шаг после того, как пользователь даст их формат.

## 6. Обработка ошибок

- Нет логина и нет cookie → понятная ошибка с инструкцией (не падать стэком).
- Сбой авторизации (есть «Неверный логин») → явное сообщение, exit code 2.
- Сессия истекла на середине → одна повторная авторизация, потом фейл.
- Пустой/неузнанный HTML → `scrape` сохраняет дамп и просит запустить `discover`.
- Сеть: таймауты + 1 ретрай с backoff.

## 7. Планировщик

`schedule_task.ps1` регистрирует задачу Windows Task Scheduler (ежедневно),
которая запускает `run_scrape.ps1` (выставляет `NO_PROXY`, активирует venv,
зовёт `python -m jac_scraper scrape`). Логи в `logs/`.

## 8. Тестирование

- `tests/fixtures/blank_zakaza_sample.html` — представительная верстка бланка.
- `test_parse.py` — парсинг строк, нормализация чисел, отсев заголовков/итогов.
- `test_export.py` — корректность CSV/JSON/XLSX.
- `test_session.py` — сборка тела логина и детектор «залогинен/нет» на
  фикстурах (без сети).
Все тесты офлайн (без обращения к порталу). End-to-end проверяется
пользователем после ввода логина (или мной, если логин будет предоставлен).

## 9. Граница готовности (Definition of Done на сейчас)

Готово без логина: весь код, тесты зелёные, README, планировщик, .env с
подставленным паролем. Остаётся ОДИН ручной шаг пользователя: вписать `JAC_LOGIN`
(или вставить `JAC_COOKIE`) и запустить `discover`→`scrape`. После этого —
калибровка селекторов под реальный HTML (≈5 минут) при необходимости.

## 10. Безопасность/этика

Доступ к собственному аккаунту пользователя у его поставщика, по его прямой
просьбе — легитимный бизнес-сценарий. Пароль хранится только в локальном
`config/.env` (в `.gitignore`), не коммитится. Перебор логина и скрытое чтение
браузерных cookie не выполняются.
